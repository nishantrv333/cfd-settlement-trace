Contracts for Difference · settlement design note · v1.0

How a CfD payment is calculated, tested against real settlement data

I took Settlement Day 12 April 2026, recalculated three CfD generator payments from public Elexon and LCCC data, and compared them with the payments LCCC published.

In scope: daily Difference Amounts for intermittent CfD generators. Out of scope: baseload units, private wire, supplier levies, Capacity Market and Nuclear RAB.

Behind the work

1 · ProcessFrom meter to payment

The daily generator payment as I read it from EMRS Working Practice WP1. Hover over a step for detail.

The Market Reference Price enters at the calculation step. For intermittent generators it is the hourly day-ahead price (IMRP). Later BSC settlement runs revise Metered Volumes, so the Difference Amount is recalculated at each run.

3 · FindingsWhat the published payments show

If every MWh earned a Difference Amount, then (Strike Price − weighted reference price) × generation equals the payment. Where it falls short, the gap shows how much volume earned nothing.

    4 · Impact assessmentIf a new allocation round changed the negative-price rule

    This has happened before: Allocation Round 4 moved from the six-hour rule to no payment in any negative hour. This is how I would start assessing the next change of that kind.

    What it would touch

    Systems
    Contract standing data, the Difference Amount calculation, recalculation on later runs.
    Processes
    Contract set-up, billing statements, payment disputes.
    Interfaces
    Contract details from LCCC, which would need to carry the rule for each contract.
    Data
    The rule and its effective dates per contract. Hourly prices kept as received.
    Users
    EMRS settlement operations, LCCC contract managers, generators.
    Dependencies
    Final contract terms for the round. Test data for a day with negative prices.

    Options

    OptionForAgainst
    A. Set the rule by allocation round in the calculationQuick to buildThe data shows the round does not decide the rule. Each new round is a code change.
    B. Hold the rule as dated standing data on each contract RecommendedHandles exceptions. A new contract needs data, not code.Needs the rule supplied and governed for every contract.
    C. Make the rule fully configurable (threshold hours, floor on or off)Most flexibleMore to test and control. Worth it only if rules keep changing.

    I assume EMRS already works something like option B. I would confirm that first, before proposing anything.
